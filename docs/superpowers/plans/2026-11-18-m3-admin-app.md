# Admin app (Stage 8a): implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the separate admin app from the canvas, show every announcement as a dialog, and remove the member-side vanity numbers.

**Spec:** `docs/superpowers/specs/2026-11-18-m3-admin-app-design.md`.

**Global Constraints:** Same as earlier stages, including the Postgres contract check for store changes.

## Review Focus

1. A member can't reach any `/admin` page or admin API.
2. "Keep" on a reported post clears its reports but keeps the post. "Remove" deletes the post.
3. An announcement with no pin date stops showing as a dialog after 14 days, and never shows twice to the same person.
4. The admin birthday entry validates the day and month.
5. No admin page shows Speak up senders, snack voters or Wi-Fi reporters.

### Task 1: Backend

**Changes:**
- `clearNoticeReports` in both stores, with a contract test.
- `DELETE /api/admin/reported { id }` (Keep).
- `PATCH /api/people` accepts birthday.
- Announcements: every one acknowledges, under the 14-day / pin rule. `needsYou` gets the new items.
- Member APIs drop vanity numbers: `today.picks` stops going to members, and so does the event `going` count in the Feed.

**Tests:** API tests, RED before GREEN. Commit.
